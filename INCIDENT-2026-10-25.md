# INCIDENT 2026-10-25 — Production /api/* total 500 outage

**Status: NOT a code bug. Service restoration requires a Netlify-side credential fix (see "The fix" below). The positioning/email bundle (352487e + 292b8d6) is EXONERATED — it was reverted during the incident out of caution and should be re-shipped once service is restored and Jeff approves.**

## Symptom
Every production `/api/*` route returns HTTP 500 with the app's own catch-all body:
`{"error":"Something went wrong on our side. Please try again."}`
Static shell and app.js serve fine. The API was verified healthy at 00:11 ET (bootstrap 200 after the hello-lane deploy) and ~00:24 ET (a live Admin campaign import + arm succeeded). It was found fully down after the ~01:15 ET bundle deploy.

## Root cause
`route()` (netlify/functions/lib/router.js, first line of the request path) calls
`await auth.ensureAdmin(logEvent)` — NOT wrapped in try/catch, unlike every other
opportunistic job in the preamble. `ensureAdmin` (lib/auth.js) begins with
`await store.get("email:jeff@joinsignl.com")` on **every request**.

In production the store is Netlify Blobs (lib/store.js), reached with **manual**
credentials from env vars `NETLIFY_BLOBS_SITE_ID` + `NETLIFY_BLOBS_TOKEN`
(the site's function runtime does not receive the automatic Blobs environment —
see the comment in getBlobs()). When the Blobs call throws, ensureAdmin throws,
route() throws, and api.js's catch-all returns 500 for **every** route — even
`/api/bootstrap`, which is pure static data and never touches the store itself.

The Blobs token is the failure point: the Netlify personal access token used for
this manual Blobs config was known to expire **2026-10-25**. Code version is
irrelevant to the outage: production currently serves the reverted
last-known-good tree (byte-identical to 83d8867, which was healthy at 00:11)
and still returns 500 on every route, across two separate deploys.

## Evidence
1. Production app.js right now is the OLD (reverted) code ("2 stories within 48"
   ×5, bundle markers ×0) — the revert deploy is live — yet /api/bootstrap,
   /api/health, /api/config, /api/campaigns all return 500 (12/12 burst).
2. Local mechanism proof (bundle code, commit 292b8d6, invoked via the real
   netlify/functions/api.js handler):
   - Production mode + invalid Blobs credentials → bootstrap returns the
     byte-identical 500 envelope seen in production.
   - SIGNL_LOCAL=1 (file store) → bootstrap returns 200.
   Same code, two store outcomes: healthy code, dead store credentials.
3. The local verify suite passes (1,786 checks) because it runs against the
   local file store — it structurally cannot see a Blobs credential failure.

## The fix (restores service — needs Jeff / a valid Netlify token)
1. Create a new Netlify personal access token (User settings → Applications →
   Personal access tokens). Give it a long expiry.
2. In the app site's Netlify env vars, replace `NETLIFY_BLOBS_TOKEN` with the
   new token (confirm `NETLIFY_BLOBS_SITE_ID` is still present).
3. Redeploy the site (env changes only apply on deploy — an empty
   "Redeploy:" commit push works, as used before).
4. Verify: `curl https://app.joinsignl.com/api/bootstrap` → 200, then confirm
   a campaign card read in Admin before the 08:00 ET sweeps.

## Recommended hardening (ship WITH the bundle re-ship, after Jeff reviews)
1. Wrap `await auth.ensureAdmin(logEvent)` in try/catch in route(), exactly
   like the other preamble jobs, so a store/credential failure degrades
   (admin bootstrap delayed) instead of taking down every route. Audit the
   rest of the preamble for other unguarded store reads on the request path
   (getAuthUser handles its own errors — verify).
2. Add a production-mode smoke check to the ship checklist: after any deploy,
   curl /api/bootstrap AND one authenticated Admin read before calling it
   live. The suite alone cannot catch environment-layer failures.
3. Calendar the new Blobs token's expiry alongside the other credential
   expiries, with a reminder a week ahead. A silent midnight expiry of a
   data-layer credential is a total outage by design until fix (1) ships.
4. Re-ship the reverted bundle (352487e positioning + 292b8d6 email
   local-reach) once service is verified back — its code is proven healthy.

## Note on the 08:00 ET deadline
The campaign sweeps (in-function opportunistic sweep + scheduled function)
read campaign configs and recipient queues from the same Blobs store. Until

## Follow-up (2026-10-25 afternoon): Admin Events + Campaign tabs hang on "Loading..."

Confirmed twice live (13:07 and 14:13 ET): every other Admin tab loaded;
Events and Campaigns never did, which blocked reading campaign sent counts.
Root cause was NOT the morning's token failure — it was unbounded, serial
reads whose cost grows with data volume until the function times out:

- `store.list()` (Blobs adapter) fetched every value with one awaited
  round trip per key, strictly serially.
- `listEvents()` loaded the ENTIRE append-only `event:` log's values and
  applied its limit only after the fact.
- `GET /admin/campaign` (x4 sequential calls per tab load) each ran a
  per-campaign recipient scan PLUS `campaignSentToday()`, a full-value
  scan of every recipient of every campaign; neither handler had a
  fail-safe, so a stall or throw meant no response at all.

Fix (local commit, ships with the next bundle per the deploy-batching
rule): store gains `listKeys` (keys only) and `getMany` (bounded-
concurrency value fetches); `list()` is rebuilt on them with the same
contract. `listEvents` fetches only the newest <=1,000 keys.
Campaign sent-today total + per-lane split derive from ONE shared scan;
the campaign view now returns `sentTodayByLane` ("creators" =
creators@signlteam.com, "default" = hello@joinsignl.com) and the tab
renders it. Both handlers are guarded in the Hardening A pattern: a
store failure returns 200 with a `degraded: true` empty/zeroed payload
so the tab renders instead of hanging. New suite verify-admintabs
(20 checks: seeded 1,500-event log + lane-stamped recipients, bounding
asserted at the store boundary, store-failure degradation for both
endpoints). Full suite after the fix: 1,843 checks / 34 suites / 0 failed.
